02 / 09 The network and how we verified it 2:45 → 3:00
On screen: two-row pipeline TikZ (x → conv1 → ReLU → pool → h₁ → conv2 → ReLU → pool → h₂ → flatten → FC1 → ReLU → FC2 → log-SM → ŷ) with tensor shapes; correctness stats below

"Some context. In this class everyone built a LeNet-5 MNIST classifier in PyTorch — 97.93% test accuracy. When you call model.to("cuda"), PyTorch handles everything under the hood. I wanted to know what that actually means — so for the final I rebuilt the forward pass of that exact network with hand-written CUDA kernels. What does model.to("cuda") actually do? That's the question this project answers."

"The diagram shows the full pipeline — it walks left to right, then wraps to a second row. Two convolutional stages, each followed by a ReLU and a 2×2 max pool. Then flatten, two fully-connected layers, and log-softmax at the end. The shapes are on screen — the key thing to notice is that valid convolution with no padding shrinks the spatial dimensions at every stage, so by the time we hit flatten the whole feature map is just 320 numbers. Flatten is a no-op here — the tensor is already contiguous in memory, no data actually moves."

"Five distinct kernel types, ten kernel launches per forward pass. Activations stay on-device between launches — only the input is copied in, only the output is copied out. Weights are exported once from the trained PyTorch model as raw float32 binary files using .numpy().tofile(), then loaded at startup with a single cudaMemcpy. At runtime the engine links only against the CUDA runtime."

"Before writing a single optimized kernel I built a three-layer correctness oracle. Layer one: a plain C++ CPU reference for every kernel — nested loops, nothing clever. Layer two: each CUDA kernel diffed against the CPU reference on random inputs at 1e-4 absolute tolerance. Layer three: the full forward pass compared against PyTorch-exported log-softmax over all 10,000 MNIST test images. If anything drifted at any layer, the relevant test turned red immediately — I never had to debug 'the logits look wrong' from the top down."

"End-to-end result: max absolute error 1.91×10⁻⁵ across all 10,000 images — 50× under tolerance. Argmax matches PyTorch on every single image. Accuracy identical to PyTorch eval mode at 97.93%."

03 / 09 Background: a CUDA kernel, in one slide 1:30 → 4:30
On screen: left — Grid→Block→Thread TikZ with annotations; right — stacked pyramid: Registers / Shared memory L1 / Global DRAM with cycle counts

"Before the optimizations, one slide of background."

"A CUDA kernel launch is one program executed by thousands of threads simultaneously. Threads are grouped into blocks — up to 1024 threads per block — and blocks form a grid. The fundamental execution unit is a warp: 32 threads that run the same instruction in lockstep. Threads in the same block can cooperate through a small fast memory called shared memory and synchronize with __syncthreads(). Threads across blocks cannot interact at all."

"The pyramid on the right is what every design decision in this project comes back to. Registers are roughly 1 cycle — zero-latency if your value is there. Shared memory is roughly 20 cycles — it's an on-chip SRAM scratchpad, about 100 kilobytes per streaming multiprocessor on the RTX 4090. Global DRAM is roughly 400 cycles — it's 400 times slower than a register. The entire rest of this talk is one idea: move data from that bottom layer into the top two, reuse it, write results back once."

DON'T SKIP
  • Warp = 32 threads in lockstep — matters for why 16-thread blocks are expensive.
  • Registers ~1 cy, shared memory ~20 cy, DRAM ~400 cy. Say the numbers.
  • Shared memory is block-local. Cross-block cooperation = impossible.
ACRONYMS & PRONUNCIATIONS
SM
"ess-em" — Streaming Multiprocessor. One independent compute unit on the GPU. RTX 4090 has 128 SMs.
warp
"worp" — 32 threads that execute the same instruction simultaneously (SIMT).
SIMT
"sim-tee" — Single Instruction Multiple Threads. CUDA's execution model.
DRAM
"dee-ram" — Dynamic Random Access Memory. The GPU's main memory (24 GB on RTX 4090). ~400 cycle latency.
SRAM
"es-ram" — Static Random Access Memory. What shared memory and L1 cache are made of. Much faster than DRAM.
L1
"ell-one" — Level-1 cache. Closest cache to the compute units, ~128 KB per SM on RTX 4090.
__syncthreads()
"sync-threads" — CUDA barrier. All threads in a block wait here until every thread has reached this point.
__shared__
"shared" — CUDA keyword that allocates a variable in shared memory instead of registers or DRAM.
04 / 09 Opt. 1 — tiled shared-memory convolution 3:00 → 7:30
On screen: left — 16×16 tile + halo TikZ diagram + explanation text; right — conv_bars.png (tiled and cuDNN speedup over naive per conv shape, RTX 4090)

"First optimization: shared-memory tiled convolution. Let me start with how the naive kernel actually works, because it's the baseline everything is measured against."

"The naive conv kernel assigns one thread per output element. A thread knows its location in the output from its block and thread indices, then loops over all input channels and all filter positions — for conv1 that's 1 input channel × 5×5 = 25 multiply-accumulates per thread; for conv2 that's 10 channels × 5×5 = 250 MACs. The block is 16×16 = 256 threads, and the grid is sized to cover every output position."

"The tiled kernel changes the memory access pattern. One block now produces one 16×16 patch of the output. Before any thread computes a single MAC, all 256 threads in the block cooperate to load the input region they collectively need into shared memory. That region is the 16×16 output footprint plus a halo of K-minus-1 pixels on each side — for our 5×5 filter, K=5, so the halo is 4 pixels wide, making the loaded patch (16+4)² = 400 values per input channel. Then every thread reads exclusively from shared memory for its 25 MACs. The theoretical reuse factor is 25 — each input value needed by one thread in the tile is also needed by up to 24 other threads, so without tiling it would be loaded from DRAM 25 times. With tiling, it's loaded once."

"Now look at the bar chart. The naive kernel wins at every LeNet shape. Tiled is slower, not faster. Why?"

"Working set size. Conv1 input is 1×28×28 — that's 784 float values, 3 kilobytes. The RTX 4090 has 128 kilobytes of L1 cache per streaming multiprocessor. Conv2 input is 10×12×12 — 1,440 floats, about 6 kilobytes. Both working sets fit in L1 with room to spare. The GPU's hardware prefetcher is already keeping those values on-chip between the 25 reuses. The cooperative load we wrote in CUDA just duplicates work the hardware was already doing, and adds a __syncthreads() barrier on top. We pay the overhead without getting the benefit."

"The tile strategy isn't wrong. The regime is wrong. Next slide shows where it actually pays off."

DON'T SKIP
  • Naive: one thread per output element. blockIdx.z encodes (n, oc) — divide/mod per block not per thread.
  • Conv1: 1×5×5=25 MACs/thread. Conv2: 10×5×5=250 MACs/thread.
  • Tiled: 16×16 tile, cooperative load of (16+4)²=400 values/channel into shmem, then compute from shmem.
  • Reuse factor 25 — but 28×28=3KB and 12×12×10=6KB both fit in 128KB L1. Hardware already caches it.
  • Tiled adds sync barrier with zero benefit → loses at every LeNet shape.
  • Say "RTX 4090" out loud — this is the first chart.

05 / 09 Tiled GEMM: where tiling actually wins 1:45 → 9:15
On screen: left — text with speedup bullets (N=1→3.8×, N=64→5.0×, N=256→6.1×, N=1024→6.4×) + LeNet FC note; right — gemm_sweep.png (speedup vs batch N at 1024×1024)

"So tiling lost for conv at LeNet scale. The same idea applied to the fully-connected layers — which are just matrix multiplies, weight matrix times input — tells a completely different story."

"The naive linear kernel assigns one thread per output element. Each thread does a dot product of one weight row against one input column — for FC1 that's 320 multiply-accumulates, for FC2 that's 50. Simple, one thread, one output, loop over the inner dimension."

"The tiled GEMM kernel assigns one 16×16 block to produce a 16×16 tile of the output matrix. Threads cooperatively load a 16×16 tile of the weight matrix and a 16×16 tile of the activation matrix into shared memory, accumulate partial dot-products, then advance to the next tile pair until the full inner-product dimension is covered. The reuse: a weight tile loaded once is used by 16 different output rows simultaneously. At large enough problems the weight matrix genuinely can't stay in L1 across all those reuses — shared memory is the only way to get it on-chip."

"At LeNet's actual FC sizes — FC1 is 50×320, FC2 is 10×50 — same story as conv: the matrix fits in L1, tiling adds overhead for zero benefit. Tiled is 1.06× and 1.01× over naive."

"But sweep to a realistic 1024×1024 weight matrix and vary batch size. At batch 1, tiled is already 3.8× faster. By batch 64 it's 5×, by batch 256 it's 6.1×, and batch 1024 hits 6.4×. The weight matrix at 1024×1024 is 4 megabytes — nowhere near L1. Loading a 16×16 tile once and reusing it across 16 output rows is a genuine DRAM-access reduction. Same kernel, same tile code, completely opposite result — the regime is the variable."

DON'T SKIP
  • Naive linear: one thread per output, one dot product. FC1=320 MACs, FC2=50 MACs.
  • Tiled: 16×16 block → 16×16 output tile. Load weight tile once, reuse across 16 output rows.
  • FC1 (50×320) and FC2 (10×50) are too small — L1 absorbs the reuse anyway. 1.06× and 1.01×.
  • 1024×1024 = 4MB → can't fit in L1 → tiling actually saves DRAM reads. 3.8× → 6.4×.
ACRONYMS & PRONUNCIATIONS
GEMM
"gem" — General Matrix Multiply. The operation C = A × B. Fully-connected layers are GEMMs.
FC
"eff-see" — Fully Connected. FC1: 320→50. FC2: 50→10.
inner product dimension
The shared dimension in a matrix multiply — e.g. the 1024 in (N×1024) × (1024×M). Larger = more reuse opportunity for tiling.
06 / 09 Opt. 3 — conv + bias + ReLU + pool fused 2:45 → 12:00
On screen: left — unfused vs fused memory-traffic TikZ (conv→DRAM→ReLU→DRAM→pool vs single fused block, shmem+registers only); right — fused_bars.png

"Third optimization: kernel fusion. The idea is to collapse three back-to-back launches — convolution, ReLU, max pooling — into one kernel that keeps everything on-chip."

"In the unfused path, the conv kernel writes a full activation tensor to DRAM. The ReLU kernel reads it back, applies max-with-zero, writes again. The pool kernel reads the ReLU'd activations and writes the pooled output. That's two full activation-sized round-trips through 400-cycle DRAM between three launches, plus three separate kernel launch overheads."

"The fused kernel eliminates all of that. The core design: one thread produces one pool output element. A pool output is the max of a 2×2 window of ReLU'd conv outputs — so each thread needs to compute four conv outputs, one per position in its 2×2 window. We keep those as four register floats, initialized to the bias so the bias add is free. Then we loop over input channels: for each channel, all threads in the block cooperate to load the input patch they collectively need into shared memory, sync, then each thread independently accumulates its four conv outputs from shared memory. No DRAM touched at all for the intermediates."

"After the channel loop: ReLU all four accumulators in registers, take the max of the four — that's the 2×2 pool. One DRAM write per thread for the entire conv-bias-ReLU-pool sequence."

"Results: conv1 at batch 1, naive is 1.76× slower than fused. At 28×28 input with 10 output channels, the launch overhead and three DRAM round-trips dominated — the kernel barely had compute to do. Fusing wins."

"Conv2 at batch 1, fused is 0.40× naive — 2.5× slower. Conv2's pool output is 4×4 per output channel. With a 4×4 block, that's one block per output channel. With 20 output channels and batch 1, we launch 20 blocks of 16 threads total — 320 threads across a GPU with 128 streaming multiprocessors. One or two SMs have any work. The other 126 are completely idle. The three separate kernels at least launch larger grids that keep more SMs busy. Fusion eliminated DRAM round-trips but also strangled the grid size. You can't optimize one without knowing what it does to the other."

DON'T SKIP
  • Unfused: 2 DRAM round-trips + 3 launch overheads.
  • Fused: one thread = one pool output. 4 register accumulators (acc00/01/10/11), initialized to bias[oc].
  • Cooperative shmem load: (2×4+4)²=144 values/channel, 16 threads → each loads 9 elements.
  • After channel loop: ReLU 4 accumulators in registers → 2×2 max → one DRAM write.
  • POOL_TILE=4: fits conv2's 4×4 output exactly, tiles conv1's 12×12 with 3×3 grid.
  • conv1: 1.76× speedup (launch overhead was the bottleneck).
  • conv2: 2.5× SLOWER — 20 blocks × 16 threads = 320 threads on 128 SMs. GPU starved.
ACRONYMS & PRONUNCIATIONS
POOL_TILE
"pool tile" — Compile-time constant (=4) setting the block tile size for the fused kernel.
occupancy
Fraction of the GPU's maximum concurrent warps that are actually active. Higher = more work in flight to hide latency.
grid
The full 3D array of blocks launched by one kernel call. Grid size = total_outputs / block_size (rounded up).
kernel launch overhead
Fixed CPU-side cost (~5–10µs) to enqueue a kernel on the GPU, independent of how much work the kernel does.
07 / 09 Resource usage and cuDNN reference 1:30 → 13:30
On screen: left — resource table (kernel / block / regs / smem, no occupancy column); right — e2e_bars.png (naive vs tiled end-to-end, RTX 4090)

"The table on the left shows static resource usage per kernel — registers and shared memory from nvcc -Xptxas=-v at compile time. Hardware profiling counters were blocked on the machine we used, so this is what we had. The key reading: no kernel spills to local memory, and every 256-thread-block kernel hits theoretical 100% occupancy. The log-softmax block is only 16 threads — next power-of-two above our 10 output classes — which limits occupancy, but it runs in about 1.8 microseconds so it's not a bottleneck."

"The bar chart shows end-to-end forward pass: naive vs tiled. Tiled pipeline is 1.21× faster at batch 1, 1.25× at batch 64. Modest, because the FC layers are tiny and conv tiling regressed — these are two known results combining."

"For the stretch tier I wrapped cuDNN's convolution API. At batch 1, our naive direct convolution beats cuDNN — descriptor initialization and algorithm dispatch overhead per call dominates when the actual compute is microseconds. At larger synthetic shapes cuDNN pulls ahead, which is expected — it's selecting Winograd and implicit-GEMM algorithms that our direct kernel doesn't implement."

"One precision gotcha worth calling out: cuDNN on this GPU silently defaults to a reduced-precision format called TF32, which truncates the floating-point mantissa from 23 bits to 10 before multiplying. Our error against the CPU reference jumped to 5.3×10⁻³ — 50× over our tolerance — with no warning. The fix: pin the math type to true FP32. Error drops back to 2×10⁻⁶."

DON'T SKIP
  • nvcc -Xptxas=-v at compile time: registers, smem, spills. No hardware counters needed.
  • log_softmax block=16 (next pow2 above 10 classes). Low occupancy but ~1.8µs — not a bottleneck.
  • cuDNN loses at batch=1 (descriptor overhead). Wins at large synthetic shapes (Winograd/implicit-GEMM). Say both.
  • TF32 = silent 50× tolerance violation. Fix: CUDNN_FMA_MATH.

09 / 09 Discussion and reflection 45 s → 15:00
On screen: four bullets, italic reflection sentence, "Thank you.", GitHub URL

"Four takeaways. Tiling isn't default-on — it hurts at LeNet, wins 6.4× at large GEMM. The regime decides. Launch overhead is real — fusion bought 1.76× on conv1 and lost 2.5× on conv2, same kernel, opposite outcome. FP32 parity with cuDNN requires opt-ins — TF32 is on by default on Ada, breaks tolerance silently. The correctness oracle chain paid for itself — 11 per-kernel tests plus 10k end-to-end meant I chased throughput without ever debugging drifting logits."

"The biggest lesson: the optimization and the speedup are separate things. Every change I made was conceptually correct. Three of them empirically slowed LeNet. Having the CPU reference first and keeping parity green on every commit made that painless to discover."
